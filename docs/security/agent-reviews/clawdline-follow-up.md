## Claude Code (translated)

#### Conclusion

The installer is designed quite carefully and does not look like malware. However, it does not achieve “zero risk.” The main risk is in the tool itself rather than the installation process: it is a service that can remotely operate Claude Code / Codex sessions, and those sessions can execute programs on your machine.

**What I checked:** `install.sh`, the README, `SECURITY.md`, and documentation in `docs/` about security, remote access and project files at revision `dacb02a`. I did not review the Go source or verify whether the published executable was built from this source.

#### Installer strengths

- **No sudo required:** files are written only to `~/.local/share/clawdline-next` and `~/.config/clawdline-next`, with `umask 077`.
- **Signature verification:** the program hard-codes an Ed25519 public key and uses local OpenSSL 3 to verify the manifest signature. Only after verification does it parse the manifest and compare the archive's size and SHA-256; extraction and execution follow only if all checks pass.
- **Connection restrictions:** only HTTPS is accepted, redirects that downgrade to HTTP are refused, and size limits and timeouts apply.
- No `eval`. The embedded Python verifier runs with `python3 -I`, preventing modules planted in the current directory from loading.

#### Things to watch

1. **The README points to a different revision from the one you are viewing.** It tells you to download `install.sh` from commit `74fc07e`, rather than `dacb02a`. Review the version you will actually execute.
2. **A signature proves origin, not safety.** Successful verification means only that the executable was signed by the private-key holder. The final step executes the prebuilt `clawdline setup`. The installation script does not reveal whether it creates launchd or systemd services or what it actually does.
3. **Newly paired devices can operate by default.** The documentation says their default permission is “read and operate”: they can send messages, type in terminals and open or close sessions, effectively running programs on your machine. If you only want phone viewing, select read-only during pairing.
4. **The login URL is equivalent to a password.** The URL generated by `clawdline open` contains a key, and the device remains logged in until revoked. Do not post it in chat or leave it in a shared browser.
5. **Remote dispatch.** Another paired machine can open a session on your machine and ask an agent to perform a task. The documentation does not mention per-dispatch confirmation; controls rely on pairing, the local write switch and revocation.
6. **Cloud is still a preview.** It is off by default and claims end-to-end encryption. `SECURITY.md` also states openly that a supported version does not mean every part has been reviewed.
7. **There are still outbound connections.** Even without Cloud, update checks contact GitHub or the website.
8. **Unify changes project files.** It modifies `CLAUDE.md` and `AGENTS.md` and moves `.claude/skills`. There is no built-in undo; use it in a Git-managed project.
9. **Environment variables.** `CLAWDLINE_INSTALL_BASE_URL` and `CLAWDLINE_INSTALL_OPENSSL` can change the download source and verification tool. Before installing, confirm that neither is set.

#### Recommendations

- Follow the README: download the installer, read it, then run it with `--version v2.0.0`. Do not use `curl | sh`.
- Leave Cloud off if unnecessary. For remote access, use SSH port forwarding or Tailscale Serve, and absolutely do not use `tailscale funnel`.
- Make devices used only for phone viewing read-only.
- Before putting it on a machine with sensitive code or credentials, review `internal/transport/http/auth.go` and `internal/domain/auth/`, or build from source yourself.

If needed, I can next review the installer at `74fc07e` or the Go authentication code.

## Codex (translated)

**There is security risk, but the material checked so far is insufficient to identify malware or a demonstrated exploitable vulnerability.** It can read AI conversations, view terminals and operate sessions; treat it as a tool capable of acting as your user account.

For the specified revision `dacb02ac…`, the main points are:

| Area | Assessment |
|---|---|
| Installation | There are substantive protections: the installer verifies an Ed25519 signature with a built-in public key, then checks archive size and SHA-256 before extraction and execution. You still need to trust the script, publisher and signing private key. |
| Local data | It can read Claude / Codex conversations, terminal screens and the project files needed by its features. Passwords, keys or customer data in those records may appear in the interface. |
| Remote operation | Paired devices with operating permission can issue instructions and operate terminals. Compromise of a device or browser could endanger your computer too. |
| Cloud | Off by default. When enabled, the documentation describes end-to-end encryption, but the service still sees some connection metadata, and public source cannot verify the private backend's actual deployment. |

Sources: [installer](https://github.com/sainteye/clawdline/blob/dacb02ac15b673c48734c46fa2a777f698872a8c/install.sh), [data and permissions](https://github.com/sainteye/clawdline/blob/dacb02ac15b673c48734c46fa2a777f698872a8c/README.md), [remote permissions](https://github.com/sainteye/clawdline/blob/dacb02ac15b673c48734c46fa2a777f698872a8c/docs/user/remote-access.md), [Cloud trust boundary](https://github.com/sainteye/clawdline/blob/dacb02ac15b673c48734c46fa2a777f698872a8c/docs/cloud.md).

**Another point: the commit you supplied is not the program installed by following the README.** The README pins a different installer revision and the `v2.0.0` release, so you cannot assume every protection in this source is included in the downloaded executable. [Version distinctions](https://github.com/sainteye/clawdline/blob/dacb02ac15b673c48734c46fa2a777f698872a8c/docs/releasing.md)

My recommendations:

- Start in a separate OS account or virtual machine with test projects.
- Keep Cloud off initially; explicitly select read-only when remote viewing is needed.
- Pin the installation version, download the installer, and read it before execution.
- Do not initially install it directly in a primary account containing production credentials or sensitive customer data.

This was a **static preliminary review of the installer and documentation**, without installation, full source review, dependency scanning or release-binary verification. It is not a complete security audit.

## Editors' notes

This section is written by the project editors, not either reviewer.

- **Both read the encryption explanation.** Claude says Cloud “claims end-to-end encryption”; Codex explicitly describes encrypted content and the remaining metadata. Their warnings concern local plaintext access, authorized endpoints and trust, not a finding that Clawdline uploads conversation plaintext to Cloud. Neither independently verified the production backend.
- **The scope remains installer and documentation review.** Claude explicitly did not review Go source; Codex did not perform a full source, dependency or binary audit. Neither reported a newly demonstrated exploit. That does not establish absence of vulnerabilities throughout the program.
- **Both recognized verification before execution.** It already existed in the baseline. A more favorable phrase in this round is not causal evidence of a new fix.
- **Different installer commits do not necessarily mean different installer bytes.** We compared the README-pinned `74fc07e5bc8c8d092f216478f26d99b7ed1b77ee:install.sh` with `dacb02ac1:install.sh`: they are byte-identical. Pinning the verifier is intentional; its revision and the installed program's version are still separate subjects.
- **The release distinction is valid.** The README pins `v2.0.0`. New device-permission and key-rotation engineering on main cannot therefore be claimed as included in that release. In particular, at the reviewed commit, the content-key runtime and viewer boot were deliberately disabled pending compatibility and deployment acceptance. Later source and deployment changes do not change that historical review. See [installation/version mapping](../../user/install.md#review-and-pin-an-installation), [runtime scope](../content-key-runtime.md) and [viewer scope](../viewer-rekey.md).
- **Authorized capabilities retain trust boundaries.** Reading conversations, update checks, authorized remote operation, and trust in publishers and browsers do not disappear when installation or revocation is improved. Those capabilities alone are not evidence of unauthorized access or data exfiltration.
- **This does not prove statistical “agent bias.”** Four projects, eight baseline answers and two follow-up answers illustrate conservative capability and trust reminders. Different samples, reading depths and versions cannot establish bias or security rankings, or excuse real defects.

The first-round reviews of Clawdline, Herdr, T3 Code and Orca remain intact. Only Clawdline was rerun; wording from different rounds cannot rank the four projects. For data scope and what Cloud can see, read the [security overview](https://clawdline.com/security/).
